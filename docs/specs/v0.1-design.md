# Agent Continuity Guard v0.1 Design

Status: Approved

Approval date: 2026-08-08

Canonical public path: docs/specs/v0.1-design.md

Distribution name: agent-continuity-guard

Python package: agent_continuity

Command: acg

Licence: MIT

Minimum Python: 3.11

## 1. Decision

Build Agent Continuity Guard, abbreviated ACG, as a standalone, public,
vendor-neutral Python repository.

ACG detects and blocks continuity failures at explicit command, harness-hook,
and CI boundaries. It binds long-running work to immutable identities, detects
evidence and documentation rot, verifies parent-child agent lineage, and
improves its own bounded rule set through deterministic proof.

ACG is not a continuous agent controller. Version 0.1 has no daemon, installs
no hooks, edits no guarded repository, and requires no network service.

The default improvement policy is deterministic automatic promotion. Human
review is an optional policy. Neither automation nor a human may bypass failed
or unknown machine proof.

## 2. Problem

Long-running agent sessions fail in repeatable ways:

- source, instructions, policy, or evidence change after a conclusion;
- documentation continues to describe paths, anchors, commands, or status
  claims that no longer match the repository;
- a session resumes from stale context after compaction or interruption;
- a subagent reviews a different base, exceeds assigned scope, or returns
  evidence that cannot be linked to its parent checkpoint;
- a green command is mistaken for complete evidence when tests were absent,
  output was truncated, or later gates never ran;
- manual learning records accumulate without deterministic deduplication,
  regression proof, promotion, or rollback;
- a guard weakens its own baseline and then declares the weaker policy valid.

Individual tools address pieces of this problem. ACG combines exact identity,
freshness, lineage, content integrity, replay, and bounded learning into one
enforcement profile.

The product may claim an integrated and differentiated enforcement model. It
must not claim to be the first continuity or checkpointing system.

## 3. Goals

Version 0.1 must:

1. Capture immutable target, instruction, policy, ruleset, goal, evidence, and
   open-work identities.
2. Produce atomic checkpoints that can be verified and resumed.
3. Detect direct and transitive evidence invalidation.
4. Detect deterministic content rot through explicit path and byte-span
   citations, changed cited bytes, stale structured claims, and evidence
   invalidation.
5. Create immutable assignments for subagents and reject misbound results.
6. Preserve exact replay as idempotent and reject conflicting replay.
7. Retain and deduplicate every non-PASS finding from state-changing
   operations; pure verification returns the same finding without persistence.
8. Generate or ingest bounded declarative candidate rules.
9. Automatically promote an eligible additive rule after complete
   deterministic proof.
10. Keep all guarded targets read-only.
11. Run offline with a standard-library runtime.
12. Produce stable machine-readable JSON and useful human-readable reports.
13. Support the portable kernel, store, and immutable Git-object verification
    on Linux, macOS, and Windows. Live-worktree promotion is supported only on
    platforms whose adapter proves every required filesystem capability.
14. Ship provenance-controlled public-safe MIT code.

## 4. Non-goals

Version 0.1 is not:

- autonomous source-code remediation;
- model training, weight learning, embeddings, or a memory/RAG system;
- an arbitrary-prose semantic truth oracle;
- an agent sandbox or permission broker;
- a secret vault;
- a daemon, scheduler, watcher, or hook installer;
- a distributed or multi-host state system;
- a remote-attestation system;
- a replacement for Git, CI, signing, backups, or incident response;
- protection against root, administrator, or a malicious same-UID process able
  to replace the kernel, state, and every audit anchor together;
- an automatic updater for the kernel, DSL, trust root, schemas, corpus labels,
  adapter trust, suppressions, exceptions, or baselines;
- a public adapter for any private reference system.
- a built-in Codex, Claude Code, GitHub Actions, or other vendor-specific
  adapter; version 0.1 accepts their data through the generic JSON seam.
- a general Markdown or documentation renderer compatibility engine.

Unstructured semantic suggestions may be reported as advisory findings. They
cannot become blocking evidence without conversion into deterministic facts
and proof.

## 5. Authority model

ACG has two authority planes.

### 5.1 Trusted deterministic kernel

The trusted kernel owns:

- CanonicalJSON/v1;
- domain-separated SHA-256 identities;
- record and fact schemas;
- verdict aggregation;
- evidence invalidation;
- assignment lineage;
- the bounded rule DSL;
- rule evaluation and monotonicity;
- promotion gates;
- audit-chain validation;
- state-directory security requirements.

The pure kernel receives immutable values. It has no filesystem, environment,
clock, subprocess, database, or network access.

### 5.2 Untrusted proposal plane

The following are untrusted data:

- repository content and instructions;
- LLM output;
- parent and subagent narratives;
- external adapter payloads;
- candidate rules and rationale;
- command output;
- human-readable reports.

Untrusted content is parsed as strict bounded data. It is never imported,
evaluated as Python, interpolated into a shell, or allowed to select trust
anchors, commands, corpus labels, adapters, or acceptance gates.

### 5.3 TrustRoot/v1

The trust-root identity binds:

- installed kernel version and distribution digest computed from the installed
  wheel RECORD plus a canonical rehash of every installed package file;
- canonicalization and hash-domain versions;
- fact-schema registry;
- DSL grammar and resource limits;
- verdict and promotion semantics;
- trusted corpus-label roots;
- trusted built-in adapter identities;
- state-directory security policy.

Learned rules are governed state, not trust-root material.

Trust-root changes require a normal release transition plus either a
previous-trusted-version cross-check or an independent verifier attestation.
The current kernel cannot approve weakening its own acceptance logic.

Editable, source-tree, missing-RECORD, or otherwise unverifiable installations
may evaluate and report, but promotion is UNKNOWN. Development promotion tests
must install a built wheel into an isolated environment. Runtime trust-root
upgrade is deferred; version 0.1 verifies a trust transition only as a release
gate.

Hash chains are tamper-evident, not tamper-proof without an external anchor.

## 6. Architecture and deep modules

The ordinary caller interface is an ergonomic facade:

    Continuity.initialize(...)
    Continuity.checkpoint(...)
    Continuity.verify(...)
    Continuity.delegate(...)
    Continuity.accept_result(...)
    Continuity.resume(...)

    Assignment.checkpoint(...)
    Assignment.complete(...)

Advanced deterministic replay uses:

    kernel.evaluate(EvaluationCase) -> EvaluationResult

Improvement uses:

    PromotionGovernor.evaluate(PromotionSnapshot) -> PromotionDecision
    PromotionGovernor.apply(
        decision_id,
        expected_ruleset_head,
        expected_audit_head,
    ) -> PromotionReceipt

These are deep modules:

- Continuity hides capture ordering, double observation, state transactions,
  invalidation, audit linkage, and automatic learning.
- Assignment hides child lineage, scope enforcement, evidence requirements,
  and result sealing.
- kernel.evaluate hides the complete pure policy and proof graph.
- PromotionGovernor reloads the canonical decision snapshot, repeats
  commit-time identity checks, and hides all sixteen promotion gates and atomic
  activation. A caller-supplied decision object is never commit authority.

The command-line interface and harness integrations are adapters. They contain
no verdict, lineage, invalidation, or promotion policy.

The flow is:

    harness or CLI event
      -> capture immutable observations
      -> build EvaluationCase
      -> kernel.evaluate
      -> PASS, WARN, BLOCK, or UNKNOWN
      -> atomic checkpoint transition when allowed

    verified failure
      -> deduplicated Finding
      -> bounded Candidate Rule
      -> Promotion Proof
      -> deterministic double evaluation
      -> atomic ruleset generation
      -> audit receipt and rollback point

## 7. Domain language

Target
: A read-only Git repository or directory observed by ACG.

Observation
: An immutable fact captured from a target, harness, actor, command, or
  explicit logical clock.

Evidence
: An observation bound to an exact target identity, producer identity,
  checkpoint, and validity interval.

Claim
: A proposition supported by identified evidence.

Invalidation
: A deterministic reason an evidence record or claim is no longer current.

Checkpoint
: An atomic continuity snapshot binding target, goal, criteria, instructions,
  policy, ruleset, actors, evidence, open work, and lineage.

Assignment
: An immutable child-agent work contract derived from one parent checkpoint.

Assignment Result
: Child output and evidence bound to exactly one Assignment.

Finding
: A normalized non-PASS outcome retained for reporting and learning.

Candidate Rule
: One bounded additive declarative protection proposed from verified findings.

Promotion Proof
: Positive reproduction, negative controls, mutation proof, corpus replay,
  monotonicity proof, and deterministic-evaluation evidence.

Ruleset
: An immutable ordered set of built-in and promoted declarative rules.

Audit Event
: A canonical event linked to the previous audit-event digest.

Verdict
: PASS, WARN, BLOCK, or UNKNOWN.

Profile
: Policy mapping findings and uncertainty to transition permission.

## 8. Verdict and enforcement semantics

Verdict precedence is:

    PASS < WARN < UNKNOWN < BLOCK

PASS means all required facts were proven and no rule fired.

WARN means a known non-blocking rule fired.

UNKNOWN means required proof was missing, stale, unsupported, truncated,
unstable, malformed, or produced by an untrusted path.

BLOCK means a deterministic blocking rule or invariant was violated.

UNKNOWN never becomes PASS.

Built-in profiles:

- observe: retains true verdicts but allows ordinary transitions. Store
  corruption, target mutation by ACG, or invalid audit identity still refuses.
- guard: default. BLOCK and required UNKNOWN refuse checkpoint advancement,
  resume, result acceptance, and promotion. WARN allows.
- strict: WARN, UNKNOWN, and BLOCK refuse protected transitions.

An EvaluationResult contains both verdict and transition_allowed. Reports do
not rewrite a BLOCK as WARN merely because an observe profile allows progress.

CLI exits:

- 0: PASS, or policy-allowed WARN;
- 1: BLOCK, fail-closed UNKNOWN, or strict-policy WARN;
- 2: invalid request, configuration, schema, or record reference;
- 3: integrity, concurrency, store, or internal invariant failure.

Canonical JSON is written to stdout. Sanitized diagnostics are written to
stderr. Human formatting is derived only from validated canonical results.

## 9. Canonical records and identity

### 9.1 CanonicalJSON/v1

Canonical records use UTF-8 JSON with:

- NFC-normalized human semantic strings;
- sorted object keys;
- compact separators;
- no insignificant whitespace or trailing newline;
- integers, strings, booleans, null, arrays, and objects only;
- no floats, NaN, Infinity, duplicate keys, control characters, or unknown
  fields;
- UTC RFC 3339 timestamps with Z;
- explicit byte encoding for every identity-bearing path and link target.

Identity-bearing paths are never Unicode-normalized or decoded and re-encoded.
PathIdentity/v1 contains:

- encoding: posix-bytes, git-path-bytes, or windows-utf16le;
- raw_b64: unpadded base64url of exact bytes;
- segment_offsets: integer byte offsets;
- case_key_b64 when the filesystem is case-insensitive.

Adapters reject absolute paths, dot-dot segments, NUL, empty segments, and case
collisions from exact bytes. Human display paths are derived, escaped, and
excluded from identity records. Symlink targets use the same raw-byte
representation.

Timestamps are ordinary record data. They affect an identity only when present
in that record. Policy evaluation uses an explicit logical time; it never reads
ambient time.

### 9.2 Domain-separated identifiers

Every immutable record identifier is:

    sha256(
      "acg" + NUL
      + record_type + NUL
      + schema_version + NUL
      + canonical_record_bytes_without_id
    )

The identifier is encoded as lowercase hexadecimal with its algorithm and
domain retained in the schema.

Every loaded record is re-canonicalized and rehashed before use.

### 9.3 Record families

TargetIdentity binds:

- adapter identity and version;
- sanitized remote identity when Git is used;
- HEAD and tree when present;
- index manifest;
- worktree manifest;
- tracked and nonignored-untracked inventory;
- object type and mode;
- raw PathIdentity records and symlink-target bytes without dereference;
- ignore-file provenance;
- platform and filesystem capability;
- physical-root fingerprint.

Raw physical paths remain local locator data and are excluded from exported
records by default. Remote credentials, query strings, and fragments are
forbidden.

InstructionIdentity binds an ordered explicit instruction manifest supplied by
policy or caller and the byte digest of every named instruction file. ACG does
not claim to discover every controlling instruction across vendors. A missing
or incomplete required manifest is UNKNOWN.

PolicyIdentity binds authoring policy, compiled policy, profile, resource
limits, and promotion mode.

Evidence binds:

- kind and subject;
- authority: deterministic or advisory;
- producer name, version, and digest;
- target and checkpoint identities;
- observed and expiry times;
- terminal exit status when applicable;
- completeness and pagination state;
- payload digest and approved structured facts;
- invalidators.

Checkpoint binds:

- parent checkpoint;
- target, goal, acceptance criteria, instructions, policy, and ruleset;
- accepted decisions and pending work;
- evidence and invalidation graph;
- actors;
- open assignments;
- audit parent.

Assignment binds:

- parent checkpoint;
- target, policy, ruleset, and instruction identities;
- task and non-goals;
- normalized allowed paths;
- declared read-only or scoped-write authority;
- required evidence;
- issue and expiry times.

ACG itself never exercises scoped-write authority. The field records what a
separate agent was allowed to do.

AssignmentResult binds:

- assignment and parent checkpoint;
- child checkpoint;
- inspected base and final target identities;
- evidence;
- changed-path manifest;
- unresolved items;
- producer and harness metadata;
- terminal state.

Finding binds:

- stable code;
- originating detector and rule;
- normalized subject;
- verdict;
- evidence and invalidation identities;
- secret-safe message identifier and parameters.

CandidateRule, PromotionDecision, RulesetGeneration, and AuditEvent are
specified in the improvement and storage sections.

## 10. Capture and target safety

Target adapters expose observation only. No target-write method exists.

ACG refuses a state root located inside the target, its Git directory, or any
resolved descendant of either.

Security-sensitive reads:

- open an approved root first;
- walk descendants without following symlink or reparse-point components;
- require expected object types;
- bind owner, mode or ACL capability, device, inode or file ID, link count,
  size, and modification identity before and after reading;
- hash bytes from one open descriptor;
- reject special files;
- reject multiple hard links for guard-owned state;
- bind symlinks as object type plus link-target bytes without dereference.

Capture uses one immutable byte view and bounded revalidation:

1. Snapshot A builds the complete path census and content manifest. Tracked
   immutable Git content is read from exact object IDs. Worktree, dirty, and
   untracked content needed by analyzers is read once through pinned
   descriptors into a private ephemeral view outside the target.
2. Snapshot B rechecks root and directory identities, repeats the path census,
   and rehashes every entry whose file identity changed plus every
   authority-critical or cited entry. The census and resulting manifest must
   match Snapshot A.
3. Snapshot C performs the same bounded revalidation immediately before
   checkpoint-head advancement.
4. Ruleset promotion performs its own commit-time target, ruleset, corpus,
   decision, and audit-head revalidation; it never relies on a prior
   checkpoint Snapshot C.

This avoids three unconditional full-content scans. It does not claim a
filesystem-wide atomic snapshot. A file that changes and returns to identical
bytes is semantically unchanged. A hostile same-UID process able to replace
content while restoring every observed file identity is outside the v0.1
threat model unless an immutable Git-object or filesystem-snapshot adapter is
used.

One complete capture retry is allowed after an unstable file. A second
instability returns UNKNOWN.

Raw source bytes are not persisted in the StateStore. Ephemeral analyzer bytes
use private temporary storage or memory, are deleted at operation end, and
produce only approved facts, raw path identities, sizes, types, and digests.

Default resource limits, all identity-bound through policy:

- 250,000 observed paths;
- 1 GiB maximum individual regular file;
- 20 GiB aggregate hashed bytes;
- 4 MiB maximum text file presented to content analyzers;
- 8 MiB maximum external adapter JSON payload.

Exceeding a required limit returns UNKNOWN. A policy change to a limit
invalidates dependent evidence.

Git observation is read-only:

- no fetch, checkout, reset, branch, index update, hook, or network action;
- lazy fetch, replacement objects, optional locks, global ignore files, and
  system ignore files are disabled;
- repository ignore files and local exclude files are digested;
- tracked and nonignored-untracked bytes are inventoried separately;
- Git-object and worktree identities remain distinct.

Filesystem observation uses a deterministic directory inventory. A policy may
define explicit exclusions, whose bytes and policy identity are bound.

## 11. State store and audit

State is external local SQLite using Python's standard library.

Default roots:

- macOS: Library/Application Support/agent-continuity-guard under the user
  home;
- Linux: XDG_STATE_HOME/agent-continuity-guard, falling back to
  .local/state/agent-continuity-guard under the user home;
- Windows: LOCALAPPDATA/agent-continuity-guard.

ACG_STATE_HOME may specify an absolute override. Relative overrides are
invalid.

The store uses:

- journal_mode DELETE;
- synchronous FULL;
- foreign_keys ON;
- BEGIN IMMEDIATE for writes;
- immutable content-addressed record rows;
- append-only audit-event rows;
- mutable, rebuildable head projections;
- expected-head compare-and-swap.

Triggers reject update or delete on immutable tables.

Store schema version 1 is frozen for v0.1. An unsupported version is an
integrity error; forward migration is deferred.

On POSIX, state directories must be 0700 and files 0600. Group- or
world-writable roots refuse promotion. On Windows, the capability record states
which ownership, ACL, reparse, atomicity, and durable-flush properties were
proven. Missing required capability returns UNKNOWN for promotion.

Every transaction:

1. verifies the active head record and the suffix after the most recent trusted
   AuditAnchor;
2. begins an immediate transaction;
3. compares the expected head;
4. inserts all immutable records;
5. appends the linked audit event;
6. changes the rebuildable head projection;
7. commits;
8. reopens and verifies inserted bytes and the audit head.

Crash recovery yields the complete prior transaction or complete new
transaction, never a mixed ruleset and audit state.

Audit verification detects mutation, reordering, missing links, and truncation
after a known external anchor.

AuditAnchor/v1 contains store identity, audit sequence, audit-head digest,
creation time, and optional caller-defined label. The anchor is canonical JSON
written to a caller-selected path outside the StateStore:

    acg audit-anchor export --output PATH
    acg verify-audit --anchor PATH

The export command refuses a path inside the StateStore or target. The anchor
is not a signature and does not resist an attacker who can replace both store
and anchor. Full verify-audit replays from genesis or a supplied anchor;
ordinary writes verify the trusted anchor/head and affected suffix rather than
replaying the complete chain.

Without an external anchor, ACG detects internal mutation and linkage failure
but cannot prove that the entire history was not replaced.

Rollback creates a new generation referencing a previously verified ruleset.
It appends history and never deletes or rewrites a prior generation.

## 12. Checkpoint and resume

Continuity.open validates target and StateStore separation and loads policy. It
does not initialize a target session. If no store exists, the returned facade
is uninitialized and only initialize is valid.

Continuity.initialize creates the first checkpoint from:

- exact target identity;
- goal and measurable acceptance criteria;
- active instructions;
- compiled policy and ruleset;
- current actors;
- current evidence;
- pending and unresolved work.

Initialization semantics:

- first initialization creates the target mapping, genesis audit event, and
  checkpoint atomically;
- repeating byte-identical initialization is idempotent and returns the
  existing receipt;
- a changed goal, criteria, target, instruction manifest, policy, or ruleset
  against an existing session is an AlreadyInitialized error;
- concurrent initialization has one compare-and-swap winner; a loser reloads
  and returns success only when the committed initialization is byte-identical;
- selecting a new explicit session key creates independent lineage over the
  same read-only target.

Continuity.checkpoint:

1. verifies store and parent head;
2. captures Snapshot A;
3. collects facts from the immutable view;
4. captures Snapshot B;
5. evaluates the candidate checkpoint;
6. records all non-PASS findings;
7. evaluates bounded learned candidates;
8. in automatic mode, requests commit of at most one already proof-eligible
   candidate by decision identifier and expected heads, then restarts the
   complete checkpoint evaluation under the new ruleset;
9. captures Snapshot C if advancement is allowed;
10. atomically appends the checkpoint and audit event.

Continuity.verify performs the same evaluation without changing the checkpoint
head, finding store, ruleset, or audit chain. Findings and candidates exist in
the returned EvaluationResult only. A pure verify never persists or promotes.
The explicit improve apply command evaluates and commits an eligible candidate;
protected checkpoint and result-acceptance transitions also invoke automatic
promotion under automatic policy.

Continuity.resume:

- loads and verifies the requested checkpoint;
- re-observes target, instructions, policy, ruleset, and required external
  evidence;
- computes direct and transitive invalidations;
- rejects stale authority under guard and strict profiles;
- returns a compact ResumeContext containing verified goal, criteria,
  constraints, decisions, pending work, unresolved items, open assignments,
  current evidence, and exact blockers.

Resume never silently merges incompatible instructions, rulesets, targets, or
goals.

## 13. Content-rot and evidence detectors

Version 0.1 includes deterministic detectors for:

1. target commit, tree, index, worktree, or inventory drift;
2. instruction, policy, ruleset, adapter, or kernel identity drift;
3. missing paths named by explicit Citation/v1 records;
4. changed cited file or byte-span digests;
5. stale Evidence by exact identity or explicit expiry;
6. incomplete generic command evidence: missing terminal status, absent
   declared output, truncated output, zero collected checks, or incomplete
   pagination;
7. conflicting structured Claim/v1 identifiers;
8. superseded structured claims still marked active;
9. assignment lineage gaps, cycles, expiry, scope mismatch, or wrong parent;
10. audit-chain or store-integrity failures;
11. case-colliding paths and unsupported special files;
12. advisory evidence incorrectly used as deterministic authority.

Citation/v1 is explicit data, not inferred prose. It contains a raw
PathIdentity, whole-file digest, optional byte_start and byte_end integers, and
optional span digest. Byte offsets address raw file bytes. A whole-file
citation omits offsets. A span citation requires both offsets and a digest.
Out-of-range or partially specified spans are invalid input.

Claim/v1 contains a stable claim ID, subject digest, state, evidence IDs,
expiry, and optional supersedes ID. Claim text is external or sensitive-local
narrative and is not part of deterministic comparison.

Citation and Claim records are supplied through policy, generic JSON input, or
a caller-owned tracked manifest with an explicit schema. ACG does not parse
general Markdown, infer heading-anchor algorithms, or rewrite documentation in
v0.1. Missing paths and changed exact cited bytes still provide useful
deterministic content-rot protection. General Markdown links, headings,
renderer compatibility, and declared-versus-observed inventory reconciliation
are deferred.

Plain prose contradiction and architectural correctness remain advisory. A
model may propose Citation, Claim, or Rule data, but its narrative is not
evidence.

Each blocking detector must have:

- a positive planted violation;
- a negative control;
- a mutation proving the protection has teeth;
- a complete expected-outcome table.

## 14. Subagent lineage

Continuity.delegate implicitly checkpoints if observed state changed, then
creates one immutable Assignment.

An Assignment contains exact:

- parent checkpoint;
- target base;
- goal-slice, task, and non-goal digests plus explicitly supplied
  sensitive-local display text;
- instructions, policy, and ruleset;
- allowed paths and declared authority;
- required evidence;
- issue and expiry times.

Assignment.open refuses:

- a StateStore other than the parent's shared same-machine store;
- the wrong target;
- changed relevant inputs;
- an expired or malformed envelope;
- instruction, policy, or ruleset mismatch;
- authority broader than the parent possessed.

Assignment.complete creates an immutable AssignmentResult. Missing required
evidence remains UNKNOWN. Summary and unresolved prose are sensitive-local
fields only when the caller explicitly supplies them. Exported envelopes and
deterministic identity use their digests, structured status codes, evidence
references, and external artifact digests.

Continuity.accept_result requires:

- one outstanding Assignment;
- exact parent and assignment identity;
- compatible target base, instructions, policy, and ruleset;
- evidence hashes still matching;
- no out-of-scope changed paths;
- complete required evidence;
- result not previously accepted.

Exact replay of identical result bytes is idempotent. Reuse of an assignment or
result identifier with different bytes is BLOCK. An accepted result creates a
new parent checkpoint; it never rewrites its parent.

Unaccepted narrative cannot enter authoritative parent evidence.

Version 0.1 supports same-machine parent and child processes sharing one
StateStore. Cross-machine envelope export, remote state, and distributed
acceptance are deferred.

## 15. Deterministic self-learning

Self-learning means deterministic accumulation of bounded detection rules from
already verified failures.

It does not mean:

- model training;
- Python generation or execution;
- source-code rewriting;
- trust-baseline rewriting;
- an LLM or human deciding machine truth.

Every non-PASS outcome creates a Finding in its EvaluationResult. A
state-changing operation persists or deduplicates it by detector, normalized
subject, violation fingerprint, and policy generation. Pure verify does not
write.

### 15.1 Rule DSL

One Candidate Rule adds exactly one rule over normalized kernel facts.

Allowed operators:

- eq;
- in;
- prefix;
- suffix;
- gte;
- lte;
- present;
- absent.

Rules are conjunctions only.

Rules cannot contain:

- any, not, ne, regex, glob, recursion, expression, template, import, callback,
  path read, environment read, clock, randomness, network, subprocess, or
  executable code;
- suppression, exemption, allowlist, priority override, update, or deletion;
- target writes, remediation, baseline mutation, or trust-root change;
- PASS or UNKNOWN output.

A rule emits one fixed WARN or BLOCK code and message identifier.

Compile-time limits:

- 16 KiB canonical executable rule;
- 16 predicates;
- 8 field-path segments;
- 64 ASCII identifier characters per segment;
- 256 UTF-8 bytes per string literal;
- 32 scalar values in an in-list;
- 4,096 active rules;
- 65,536 predicate evaluations per case.

Limit exhaustion is UNKNOWN.

### 15.2 Candidate authority and corpus labels

Automatic promotion requires a trusted CorpusLabel/v1 for every expected
positive, negative, and output-delta case.

A label is trusted only when:

- an existing kernel invariant or deterministic oracle derives it under the
  current trust root; or
- it was admitted through the release-controlled corpus-label process before
  candidate evaluation.

Two evidence lineages, an operator correction, proposer narrative,
proposer-created labels, and proposer-created fixtures may justify a
QUARANTINED candidate. They do not create trusted labels and cannot alone make
automatic promotion eligible.

Corpus-label admission is a trust-root/release action. It is append-only,
records provenance and independent review, changes the corpus root, and
requires the same previous-version or independent-verifier release check as
other trust-root changes. It is not performed by checkpoint, improve apply,
review approval, an adapter, or an LLM.

This creates an explicit route:

    Finding
      -> QUARANTINED candidate
      -> deterministic-oracle labels or release-admitted labels
      -> complete Promotion Proof
      -> automatic eligibility

Human review mode approves only a machine-eligible candidate. It cannot admit
corpus labels through the promotion interface.

The proposer receives a minimal redacted finding envelope and public DSL
schema, not protected corpus data by default.

### 15.3 Promotion proof

An eligible rule requires:

1. positive fixture derived from immutable evidence with a trusted label;
2. at least one trusted independently labelled safe negative control;
3. one predicate-boundary negative case per predicate;
4. candidate-removal mutation proof;
5. non-equivalent operator and literal mutants for every predicate;
6. severity-downgrade mutant;
7. 100 percent generated-mutant kill rate;
8. complete replay of the immutable corpus;
9. no unlabelled output delta;
10. syntactic and semantic monotonicity;
11. two clean-process byte-identical decisions;
12. secret and data-classification success.

### 15.4 Promotion state and order

States:

    QUARANTINED
      -> VALIDATED
      -> PROVEN
      -> ELIGIBLE
      -> PROMOTED

Holding or terminal states:

- REJECTED for a deterministic failed gate;
- DEFERRED_UNKNOWN for unavailable or unverifiable proof;
- AWAITING_APPROVAL for an eligible candidate under review policy.

Gates execute in this order:

1. strict parsing, schema, canonicalization, and size limits;
2. authority confinement;
3. candidate and rule deduplication;
4. evidence and target identity verification;
5. authoritative failure provenance;
6. positive reproduction against baseline and candidate;
7. negative controls;
8. candidate mutation proof;
9. full immutable corpus replay;
10. syntactic monotonicity;
11. semantic monotonicity;
12. two clean-process byte-identical evaluations;
13. secret and data-classification scan;
14. commit-time input and head revalidation;
15. atomic compare-and-swap generation commit;
16. readback and audit-chain verification.

Any failed gate rejects. Any missing, unstable, unsupported, or ambiguous proof
defers as UNKNOWN.

Default automatic policy promotes immediately after all gates pass.

Review policy pauses an eligible byte-identical candidate before commit. Human
approval cannot modify evaluated bytes or override a failed or UNKNOWN gate.
Changed input requires full reevaluation.

### 15.5 Monotonicity

A candidate must:

- add exactly one content-addressed rule;
- leave all existing rules unchanged;
- preserve every existing finding;
- never reduce finding severity;
- leave existing UNKNOWN reasons intact;
- add only independently labelled expected findings;
- never reduce enforcement rank.

Automatic promotion cannot create exceptions or update a permissive baseline.

### 15.6 Double evaluation and rollback

Double evaluation runs in separate clean Python processes with:

- the same installed-wheel digest;
- the same snapshot, ruleset, corpus, policy, and explicit logical time;
- empty temporary state roots;
- fixed locale and timezone;
- sanitized environment;
- no network;
- no inherited writable handles.

Canonical PromotionDecision bytes must match exactly.

Rollback is append-only. The automatic learner cannot weaken protection by
rolling back an already committed generation. Automatic restoration is allowed
only during an incomplete transaction/readback failure before a new generation
is considered committed. Later rollback requires a trusted operator or a
separately configured deterministic operational policy and leaves the guard
blocked until its cause is recorded.

## 16. Policy

Human-authored policy is TOML. The kernel evaluates a strict canonical compiled
JSON form.

Policy sources, in precedence order:

1. explicit command path;
2. target-root acg.toml, read-only if present;
3. built-in guard defaults.

ACG never creates or modifies target policy. The policy-template command writes
a template to stdout for a caller to redirect or commit deliberately.

Unknown keys, duplicate keys, wrong types, unsupported versions, or invalid
paths are errors.

Promotion modes:

- automatic: default;
- review: human approval after all machine proof;
- disabled.

Profiles:

- observe;
- guard: default;
- strict.

Policy identity includes resource limits, adapter requirements, evidence
expiry, detector selection, finding severity, and promotion mode. A policy
change invalidates dependent evidence.

        decision_id,

CLI:

    acg init
    acg checkpoint
    acg verify
    acg resume
    acg delegate

The approve command exists only in review mode. It cannot bypass proof.

The improve apply command evaluates the candidate, stores a canonical decision,

policy, or remediates target content.

## 18. Adapters

Version 0.1 includes:

- local filesystem observation;
- read-only local Git CLI observation;
- canonical generic JSON and standard-input event translation;
- in-memory state and clock adapters for tests.

Codex, Claude Code, CI, and other harnesses integrate through the generic JSON
schema in v0.1. Documentation may show caller-owned examples, but ACG ships no
vendor translator or hook installer.

Unknown payload versions, malformed JSON, partial output, timeout, truncation,
oversize, missing terminal status, or inconsistent evidence become UNKNOWN.

Version 0.1 excludes:

- Codex, Claude Code, GitHub Actions, Gemini, OpenClaw, MCP, IDE, browser,
  Slack, and remote-agent adapters;
- GitHub API calls or remote evidence retrieval;
- third-party plugin discovery or Python entry-point import;
- arbitrary external executables;
- distributed state and team authorization.

External adapter support may later use bounded JSON subprocesses. Installing or
trusting adapter code remains an explicit release or operator action.

Output-channel contract:

- stdout is always canonical ACG JSON;
- stderr is sanitized diagnostics;
- any future CI annotation output must use an explicit separate file or
  non-canonical format command and can never be consumed as canonical evidence.

Malformed top-level CLI requests or invalid ACG schemas exit 2. A valid request
containing syntactically valid but incomplete, unsupported-version, truncated,
or unavailable external evidence evaluates to UNKNOWN and exits according to
policy. Contract tests cover both paths.

## 19. Secret and privacy contract

Every fact field is:

- public;
- sensitive_local;
- sensitive_hash;
- forbidden.

Sensitive-local fields are stored only in the protected local StateStore,
excluded from exports, proposals, audit messages, and deterministic comparison
except through their digest. Explicit goal, acceptance-criterion, task,
summary, and pending-work text supplied by a caller may use this class.
Harness prompts and arbitrary transcripts are never ingested automatically.

Forbidden values include:

- environment variable values;
- credentials, cookies, tokens, and private keys;
- authorization headers;
- known secret-file contents;
- raw harness prompts, transcripts, or source excerpts not explicitly approved
  as sensitive-local by schema and caller action.

ACG persists relative path, size, type, digest, and normalized metadata rather
than source bytes.

Reports and audit events do not include raw observed values by default.

Candidate-controlled strings are length-limited, control-character-free,
escaped as data, and secret-scanned before persistence or display. A suspected
secret rejects without echoing the matched value.

Schema-level exclusion is the primary control. Secret scanning is
defense-in-depth. Version 0.1 has no encrypted secret store.

## 21. Testing and release gates

Required test classes:

- golden canonical JSON and domain-separated hash vectors;
- strict-schema positive and negative vectors;
- pure-kernel decision tables;
- property tests for ordering, replay, path normalization, and monotonicity;
- planted positive and negative controls for every built-in detector;
- CLI subprocess tests;
- temporary Git and filesystem repositories;
- symlink, hardlink, reparse-point, ancestor-swap, rename, truncation, and
  concurrent-mutation attacks;
- checkpoint and promotion compare-and-swap races;
- fault injection at every transaction boundary;
- audit mutation, reorder, link loss, and anchored truncation;
- exact and conflicting assignment-result replay;
- two clean-process promotion evaluations;
- candidate and critical implementation mutation tests;
- secret placement in every external field;
- installed-wheel end-to-end tests.

CI:

- Python 3.11, 3.12, 3.13, and 3.14;
- Ubuntu, macOS, and Windows;
- no network in ordinary tests;
- strict type checking;
- formatting and lint;
- dependency audit;
- SAST and secret scan;
- action references pinned by commit;
- independent jobs so one early failure does not hide later gate status;
- final required aggregate gate.

Coverage is supporting evidence, not sole proof.

Release thresholds:

- every enumerated security decision in canonicalization, verdict,
  invalidation, lineage, promotion, and audit has a complete branch decision
  table and 100 percent exercised decision outcomes;
- at least 90 percent branch coverage overall;
- 100 percent kill rate for generated candidate mutants;
- all critical planted implementation mutants killed;
- every blocking detector has positive, negative, and mutation evidence;
- full corpus replay byte-identical in two clean processes;
- crash and concurrency suites pass;
- clean detached source identity recorded;
- wheel and source distribution built twice and compared;
- wheel and source distribution installed and smoke-tested;
- SBOM, wheel RECORD, canonical SHA-256 artifact manifest, and CI provenance
  attestation generated by the release workflow;
- full audit verification from genesis to release head.

A platform may advertise read-only verification while promotion is UNKNOWN if
its filesystem adapter cannot prove required no-follow, atomicity, ownership,
or durable-flush behavior. Capability is never silently downgraded.

## 23. Private-reference validation boundary

Any private-reference validation occurs outside this public repository and
outside each read-only target. Public code, documentation, fixtures, rules,
reports, and Git history contain no private names, source, prose, hashes,
datasets, paths, or failure narratives.

A lesson from private validation may enter the public project only after:

1. restatement as an abstract requirement;
2. independent implementation from this public specification;
3. invention of a generic synthetic fixture;
4. provenance, similarity, secret, and forbidden-token checks;
5. complete public-corpus proof.

Private validation may produce a secret-safe pass/fail attestation for release.
Its profiles, findings, rules, and state remain private and external.

## 25. v0.1 acceptance criteria

Release requires all of:

1. Changed cited bytes invalidate affected evidence.
2. Missing, stale, unstable, truncated, or incomplete evidence cannot pass.
3. Unrelated changes are distinguished from direct invalidators.
4. Resume refuses stale checkpoints and reports exact reasons.
5. A child result cannot cross assignment, parent, target, instruction,
   policy, ruleset, or base identity.
6. Exact result replay is idempotent; conflicting replay blocks.
7. Every state-changing non-PASS evaluation persists or deduplicates a
   Finding; pure verify returns the same Finding without persistence.
8. An eligible bounded candidate auto-promotes under default policy.
9. Weakening, exception, executable, incomplete, nondeterministic, poisoned,
   or UNKNOWN candidates cannot promote.
10. Ruleset promotion and rollback are atomic, content-addressed,
    compare-and-swap protected, and append-only.
11. Audit mutation or deletion after an anchored point is detected.
12. The same PromotionSnapshot produces byte-identical decisions in two clean
    processes.
13. ACG issues no write that changes target content, Git refs, index,
    configuration, hooks, permissions, or application-controlled metadata.
    Shell redirection chosen by a caller and filesystem access-time behavior
    are outside this claim.
14. Public-source and fixture provenance gates pass.
15. Wheel and source distribution install and pass the smoke workflow on every
    declared platform.
16. State-root overlap with target or Git directory is rejected before any
    state write.
17. Observe, guard, and strict profiles produce their specified verdict and
    transition_allowed combinations for PASS, WARN, UNKNOWN, and BLOCK.
18. Checkpoint, finding, ruleset, and audit transactions recover atomically
    after injected failure at every transaction boundary.
19. Forbidden and sensitive-local fields never appear in exports, proposals,
    audit messages, or canonical stdout.
20. An unsupported filesystem capability remains explicit in TargetIdentity
    and makes promotion UNKNOWN rather than silently lowering assurance.

Acceptance-to-test traceability:

|---|---|

## 26. Alternatives rejected

Copy and generalize the private monolithic acceptance script
: Rejected. It carries platform assumptions, weak coverage, mixed authority,
  and unrelated domain behavior. ACG reimplements abstract invariants through
  invented public tests.

Harness-specific hook package
: Rejected. Fast but not vendor-neutral and unable to prove cross-harness
  lineage.

Always-running daemon
: Rejected for v0.1. It adds ownership, recovery, and availability failures
  before the deterministic kernel is proven.

LLM consensus as promotion authority
: Rejected. Multiple advisory models do not make a deterministic fact.

Arbitrary Python rule plugins
: Rejected for v0.1. They enlarge the trust root and permit candidate code
  execution.

Separate kernel and learner repositories
: Rejected for v0.1. Process isolation is useful later, but separate release
  trains add operational complexity without improving the initial pure-kernel
  seam.

Repository-local mutable state
: Rejected. It pollutes the target, creates self-invalidating evidence, and
  violates read-only operation.

Coverage-only assurance
: Rejected. Behavioral negative controls, mutation proof, replay, race, crash,
  and installed-package tests are mandatory.

## 27. Principal risks

False blocking
: Controlled by observe mode, negative controls, labelled corpus replay,
  monotonic rules, atomic rollback history, and synthetic dogfood.

Rule poisoning
: Controlled by authoritative failure provenance, corpus-label separation,
  proposer redaction, one-rule promotions, mutations, and independent replay.

Adapter drift
: Adapter identity is evidence. Unsupported or changed adapters yield UNKNOWN.

Filesystem races
: Descriptor-pinned reads, A/B/C identity confirmation, compare-and-swap, and
  adversarial race tests.

Secret leakage
: Schema-level forbidden fields, no source-byte persistence, redaction, and
  secret scanning.

Self-weakening policy
: Learned rules are additive only. Exceptions, suppressions, baseline changes,
  trust-root changes, and rollback cannot be self-promoted.

Audit overclaim
: Documentation states tamper-evident limits and external-anchor requirement.

Scope growth into orchestration
: ACG records assignments and verifies results; it does not spawn, schedule,
  supervise, or remediate agents.

## 28. Completion boundary

This design authorizes writing an implementation plan and then implementing
version 0.1 through the delivery slices.

It does not authorize:

- copying proprietary implementation text;
- operating private production runtimes;
- publishing a release before acceptance gates pass;
- weakening deterministic automatic promotion requirements;
- expanding version 0.1 into deferred network, daemon, remediation, UI, or
  plugin work.
